1Overview & status

Wordocious is a daily word-puzzle game — ten modes, daily leaderboards, real-time multiplayer — shipped by ShowLoud, LLC on three clients that share one deterministic game engine:

3The deterministic core

  • Seeded dailies. A puzzle is fully determined by its seed (daily-YYYY-MM-DD-MODE). No server round-trip is needed to start a game; every client derives the same answers from the same seed and word lists.
  • One engine, three ports. TypeScript is canonical; Swift and Kotlin ports mirror it exactly. Shared JSON fixtures (seed-fixtures, prefill-fixtures, scoring fixtures) are generated from the TS core and asserted by all three test suites — an engine change that lands without regenerating them fails the web tests first, not the native ones days later.
  • The reducer (packages/core/src/reducer.ts + ports) is the single state machine for every mode: guess validation, multi-board apply-to-all, sequential-stage advancement, Gauntlet stage chaining, prefills. UI layers never re-implement rules.
  • ProperNoundle is the deliberate exception: answers are famous names from a curated pool (669 puzzles, categories + Wikipedia clues), and guesses skip dictionary validation on every platform.

4Word bank

  • Two tiers, one player-facing "word bank". Answers are small curated lists (zipf-frequency bar ~3.0, no proper nouns, blocklists applied); guesses are far more permissive (5-letter: 10,140; 6: 11,180; 7: 12,728).
  • The G1–G8 rule set (documented in scripts/curate-solutions.py) governs the guess lists: length purity, answers-always-guessable, lexicon-derived candidates, generated inflections (-S/-ED/-ER/-ING…), offensive blocklist (applied to inflection bases too), proper-noun exclusion, monotonic growth (the guess list never shrinks — asserted in code), and a hand-vouched modern-words list.
  • History is protected by tests (apps/web/scripts/word-list-sync.test.ts): every answer ever served must stay guessable, all bundle copies must be byte-identical across the three platforms, and no shipped guess may derive from a slur. Replaying a finished game pushes stored guesses back through the reducer, so a word leaving the list would silently rewrite history — the tests make that impossible to ship.
  • Players report gaps to support@wordocious.com (invited in-app under How to Play → Which Words Count?).

5Scoring

  • V2, guess-first (days ≥ 2026-07-14): 1,000 base + a per-mode guess bonus for every unused guess (Classic 300) + a speed bonus capped at 80% of one guess-step (time only breaks ties) + completion up to 200 + hint penalties (PN 60, Six/Seven 75). Losses bank partial credit (letters, boards, Gauntlet stages).
  • V1 is frozen forever and selected by the puzzle's date, so pre-cutover leaderboards recompute exactly what was recorded.
  • Single source: apps/web/lib/composite-scoring.ts, mirrored by DailyScoring.swift / DailyScoring.kt, pinned by generated fixtures. VS matches use a separate small ELO-style breakdown in packages/core/src/scoring.ts.

6Backend (Supabase)

Project ref eniiqqsxpmuyrspvepiw — Postgres + Auth + RLS. There is no bespoke app server for game data; clients talk to Supabase directly under row-level security, and privileged writes go through Next.js API routes using the service-role key.

  • Auth: Google OAuth, Sign in with Apple (iOS), email+password with confirmation, password reset. Guests can play without an account; results then live only on-device.
  • Key tables: profiles (identity + is_pro/pro_expires_at — the single Pro entitlement all three clients read), daily_results (materialized per-day scores that power leaderboards — stats are stored, never recomputed from guesses), matches (VS history incl. guess logs), medals, streak_shields, daily_bonuses, referrals, device_tokens, announcements, reports, store_webhook_events (payments idempotency ledger), daily_seeds.
  • RLS posture: users write only their own rows with value clamps; Pro columns are locked by a trigger (protect_pro_columns_trg) so only admin/service-role can grant entitlements; moderation adds is_banned filtering and a reports pipeline.
  • Admin: profiles.role = 'admin' gates the portal at /admin (server-side in middleware.ts) and every /api/admin/* route re-verifies.

7Web app & content APIs

  • Hosting: Vercel (Pro plan), project wordocious, domain wordocious.com. Push to main = production deploy. Nothing deploys from branches.
  • Crons (vercel.json): daily medals 12:05 UTC, daily reminder push 14:00 UTC, expire-pro hourly (Pro-plan feature — on Hobby an hourly cron silently breaks ALL deploys; see bible if the plan ever changes).
  • Single-sourced editorial content: How to Play, FAQ, mode help, About, Support, Guides, Strategy, and Word-of-Day archives live in apps/web/lib/*-content.ts and are served at /api/howtoplay, /api/content, /api/guides, /api/strategy, /api/words. Both native apps fetch and cache these — editing app help copy is a web deploy, not an app release. Only Privacy/Terms are hardcoded per platform (offline compliance).
  • Public pages for SEO/AdSense: guides, strategy articles, word archives, FAQ, privacy, terms, delete-account. AuthGate keeps them crawlable while gating gameplay.

8VS multiplayer & bots

  • Live matches: socket.io server (apps/server) on Railway, auto-deployed from main. It validates guesses server-side with the same core engine and word lists, relays opponent progress, and records results.
  • Three ways to get an opponent: friend invite links (/vs/join/CODE), the live queue, or built-in bots — client-side personas with difficulty tiers including an adaptive one (BotEngine/BotPersonas per platform). Bot matches satisfy the same transport interface as the socket, so the match UI cannot tell them apart; they record under a separate vs_cpu play type that stays out of human stats.
  • Daily VS uses one shared daily puzzle; free players have a daily VS limit, Pro adds invites and rematches.

9Payments — three independent rails

Policy fact that shapes everything here: Apple mandates IAP in the iOS app, Google mandates Play Billing in the Android app, and Stripe may only sell on the web. The three rails never mix; parity of products and prices across them is a deliberate invariant.

  • Entitlement is one row: profiles.is_pro + pro_expires_at, read by each client's isProActive. A grant from any rail lights up all three platforms instantly — no build required.
  • Server-authoritative fulfillment: App Store Server Notifications → /api/appstore/notifications; Play RTDN → /api/playstore/notifications; Stripe webhooks → /api/stripe/*. All claim events in the store_webhook_events ledger (idempotent) and extend entitlement additively (Math.max pattern — a grant never truncates an existing window). An hourly cron expires lapsed Pro.

Google — merchant account created Aug 1 (identity verified, 15% small-business fee enrolled, payout bank pending micro-deposit verification); products created via scripts/play-create-products.mjs once console permission propagates.

10Ads, push, crash reporting

  • Ads: Google AdMob in both native apps (banner + interstitial), gated by consent — Apple ATT on iOS, Google UMP where required — with a persistent "Ad Privacy Settings" row in Settings. Pro removes all ads. Web uses AdSense (application under review). Emulators show Google test ads by design.
  • Push: APNs (iOS, live since build 134) and FCM (Android, code-complete; needs FCM_SERVICE_ACCOUNT in Vercel env). Tokens in device_tokens, sends via /api/push, daily-reminder cron at 14:00 UTC.
  • Crash reporting: Sentry on web, iOS, and Android, including capture of rejected Supabase writes so silent RLS failures surface.

11Referrals

  • Any signed-in player creates up to 3 pending invite links (/join/CODE, 30-day expiry). A new user who redeems gets 7 days of Pro; if they later subscribe, the inviter gets +30 days (monthly) or +60 (yearly), granted once via reward_granted_at so renewals never double-pay.
  • Anti-fraud: one redemption per account ever (DB-enforced), no self-referral, redeemer must never have had Pro, pro_day never triggers rewards.
  • Hooked into all three fulfillment paths; native apps deep-link via universal links (AASA) / Android App Links. Top Inviters leaderboard on web + native panels.

14Secrets & access

  • This document contains no secrets. Web/server secrets (Supabase service role, Stripe keys, webhook secrets, FCM service account) live in Vercel environment variables. Local signing material lives outside the repo: ~/.appstoreconnect/ (ASC API key + export plists), ~/.android-keys/ (upload keystore + Play publisher service-account JSON).
  • The Play service account is least-privilege by design: testing tracks + store presence, no production release, no financial data. Production pushes on both stores are human console actions.
  • Admin portal access = profiles.role = 'admin', enforced server-side. This page is inside that gate; the standalone HTML copy should be treated as internal.

15Conventions & guard rails

  • iOS is the design foundation; Android matches it. Render-parity audits are scoped by user flow, not by filename (bible §189).
  • Drift guards over discipline: engine parity fixtures, word-list sync tests, scoring fixtures, and content invariants all fail builds rather than relying on memory.
  • The bible (WORDOCIOUS_BIBLE.md) records every incident and decision as numbered entries — read it before re-deriving any past decision. This portal is regenerated from apps/web/lib/portal-html.ts via node scripts/gen-portal-html.mjs; a sync test keeps the copies identical.
  • Editorial copy is code: it ships through the content APIs, rots silently, and gets audited (bible §195). When a formula or feature changes, grep the content files for every description of it.
