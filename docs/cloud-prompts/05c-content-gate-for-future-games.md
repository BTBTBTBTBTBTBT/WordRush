ADD-ON (same branch cloud/content-fixes, same PR): make content safety AUTOMATIC so a new game (or a new bank/puzzle batch) never needs a manual sweep again.
1. One shared content-safety module in packages/core (TS, with the word lists as data files): isOffensive (profanity, slurs, sexual, drug, violent, hate — incl. substring/leet checks for clues and phrases), isBritishOnly, isObscure (frequency threshold from the frequency list used in 05b), mustAccept (the everyday-words list from 05b). Used by every guard and by generators; Swift/Kotlin ports only if apps need them at runtime (otherwise build-time only).
2. A content REGISTRY: every bank/answer pool/accept list/clue file for every game is registered in one manifest (game, path on web/iOS/Android, kind: answers | accept | clues | scramble | required-words, length rules). A test FAILS if any bank-like file exists in the repo that isn't registered (scan the known bank folders by pattern), so a new game can't ship an unchecked list — registering it automatically applies every guard.
3. One command for everything: `npm run content:check` (root or apps/web) runs all guards over all registered banks (offensive / British / obscure / must-accept / per-game rules / iOS-Android-web copies identical / no change to already-served past dates) and prints a readable report. Wire it into the existing test suite / CI so it runs on every PR.
4. Generators and imports use the same filters: wherever puzzles or word lists are generated or imported (scripts under apps/web/scripts, data/, docs), route candidates through the content-safety module so bad words are rejected at creation time, not found later.
5. New-game checklist: docs/CONTENT-SAFETY.md — how to add a game's banks (register → run content:check → fix flags), how to add words to the allow/block lists, and how swap batches + cutover dates work for live games.
6. Report this in REPORT-CONTENT-FIXES.md (registry contents, guard list, CI wiring, how long content:check takes).
